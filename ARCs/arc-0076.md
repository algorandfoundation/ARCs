## Abstract

This standard specifies a computation for seed bytes for Password Account. For general adoption it is better for people to remember passphrase than mnemonic. With this standard person can hash the passphrase and receive the seed bytes for X25529 algorand account.

The same seed bytes MAY also be used to derive a post-quantum Falcon-1024 Algorand account, using the standard Algorand Falcon key derivation (see [Falcon account](#falcon-post-quantum-account)).

## Motivation

By providing a clear and precise computation process, Password Account empowers individuals to effortlessly obtain their seed bytes for algorand account. In the realm of practicality and widespread adoption, the standard highlights the immense advantages of utilizing a passphrase rather than a mnemonic. Remembering a passphrase becomes the key to unlocking a world of possibilities. With this groundbreaking standard, individuals can take control of their X25529 Algorand account by simply hashing their passphrase and effortlessly receiving the corresponding seed bytes. It's time to embrace this new era of accessibility and security, empowering yourself to reach new heights in the world of Password Accounts. Let this standard serve as your guiding light, motivating community to embark on a journey of limitless possibilities and unparalleled success.

This standard seek the synchronization between wallets which may provide password protected accounts.

## Specification

Seed bytes generation is calculated with algorithm:

```
      const init = `ARC-0076-${password}-{slotId}-PBKDF2-999999`;
      const salt = `ARC-0076-{slotId}-PBKDF2-999999`;
      const iterations = 999999;
      const cryptoKey = await window.crypto.subtle.importKey(
        "raw",
        Buffer.from(init, "utf-8"),
        "PBKDF2",
        false,
        ["deriveBits", "deriveKey"]
      );
      const masterBits = await window.crypto.subtle.deriveBits(
        {
          name: "PBKDF2",
          hash: "SHA-256",
          salt: Buffer.from(salt, "utf-8"),
          iterations: iterations,
        },
        cryptoKey,
        256
      );

      const uint8 = new Uint8Array(masterBits);
      const mnemonic = algosdk.mnemonicFromSeed(uint8);
      const genAccount = algosdk.mnemonicToSecretKey(mnemonic);
```

Length of the data section SHOULD be at least 16 bytes long.

Slot ID is account iteration. Default is "0".

### Email Password account

Email Password account is account generated from the original data

```
      const init = `ARC-0076-${email}-${password}-{slotId}-PBKDF2-999999`;
      const salt = `ARC-0076-${email}-{slotId}-PBKDF2-999999`;
```

The email part can be published to the service provider backend and verified by the service provider. Password MUST NOT be transferred over the network.

Length of the password SHOULD be at least 16 bytes long.

### Falcon (post-quantum) account

Algorand supports post-quantum accounts that are authorized with Falcon-1024 signatures
([Algorand Falcon specification](https://specs.algorand.co/crypto/crypto-falcon)). The 32 seed bytes produced by
this standard (the `masterBits` above, for any `slotId` and with or without `email`) MAY be used to derive a Falcon account in
exactly the same way as they are used to derive the basic Ed25519 account: the seed bytes are the account entropy.

Given the 32 seed bytes `seed` computed by this standard:

1. The Falcon-1024 key generation seed is `SHA-512/256("PQK" || "f1" || seed)` (32 bytes), where `"PQK"` is the ASCII
   prefix, `"f1"` (`0x66 0x31`) is the two byte scheme identifier of Falcon-1024 and `||` is concatenation. This is the same
   derivation as `mnemonic.to_pq_seed` of the Algorand SDKs applied to the 32 bytes which the 25 word mnemonic of the
   basic account encodes.
2. The Falcon-1024 keypair (1793 byte public key, 2305 byte private key) is generated by the deterministic Falcon-1024
   key generation used by Algorand (`falcon_det1024`, <https://github.com/algorand/falcon>) from the 32 byte key
   generation seed of step 1.
3. The account address is `SHA-512/256("PQA" || "f1" || salt || publicKey)` encoded as a standard Algorand address, where `salt`
   is the lowest byte value in `0..255` for which this 32 byte digest does not decode to a point of the Ed25519 curve
   (the same predicate as `IsEdwards25519Point` of go-algorand). The salt is part of the account and is required to build
   the post-quantum signature envelope.

Implementations MUST NOT apply Unicode normalization or any other transformation to `email` and `password` for the Falcon
account either: the seed bytes are exactly the ones defined above, so the Falcon account of a given `email`, `password`
and `slotId` can always be re-derived from them.

The Falcon account and the basic account derived from the same `email`, `password` and `slotId` are different accounts,
but they share the same secret entropy (see Security Considerations). Wallets which want both SHOULD use different
`slotId` values for them.

## Rationale

This standard was designed to allow the wallets to provide password protected accounts which does not require general population to store the mnemonic. Email extension allows service providers to bind specific account with the email address, and user experience to feel the basic authentication form with email and password they are already used to from web2 usecases.

Post-quantum Falcon accounts are a natural extension: a person who remembers a passphrase can control a quantum resistant account
the same way as a basic account, without any extra secret to back up. Reusing the seed bytes of this standard keeps a single
derivation for wallets and services, and the Falcon key derivation itself is the one already defined by Algorand, so existing SDK
primitives can be used.

## Backwards Compatibility

We expect future extensions to be compatible with Password account. The hash mechanism for the future algorighms should be suffixed such as ```-PBKDF2-999999```.

The Falcon account derivation does not change the seed bytes, so every existing Password Account and Email Password account keeps the same
address and implementations which do not support Falcon remain compliant.

## Security Considerations

This standard moves the security of strength of the account to how user generates the password.

This standard relies on randomness  and collision resistance of PBKDF2 and 'SHA-256'. User MUST be informed about the risks associated with this type of account.

The basic Ed25519 account and the Falcon account derived from the same `email`, `password` and `slotId` have the same secret
entropy: anyone who learns the password (or the seed bytes) controls both. Post-quantum signatures do not protect the account against
a stolen or guessed password, and PBKDF2 and `SHA-512/256` are the only things standing between a password guess and the key. Users who
hold both account types SHOULD use a different `slotId` (or password) for each of them. Because the Falcon key is derived
deterministically, implementations MUST verify their output against the sample data above before using real funds.
