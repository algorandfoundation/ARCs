## Abstract

This standard defines the normative HTTP 402 Machine-to-Machine (M2M) Payment & Execution Evidence protocol for Algorand Consensus V2. It specifies standard HTTP 402 response headers, machine challenge schemas, on-chain note-field execution evidence anchoring (`x402:receipt:v1:<sha256>`), 16-transaction atomic Delivery-vs-Payment (DvP) transaction groups, and native fee-pooling sponsorship enabling zero-native-balance autonomous AI agents to execute gasless commercial transactions on Algorand.

## Motivation

Autonomous AI agents, autonomous tool runners, and high-concurrency API services increasingly require programmatic, sub-second machine micropayments. Traditional smart-contract payment channels on EVM and SVM networks incur multi-block reorg risks, gas fee volatility, upfront float requirements, and non-deterministic finality.

Algorand Consensus V2 offers structural advantages for autonomous machine commerce:
1. **Sub-3s Deterministic Finality (~2.8s)**: Pure Proof-of-Stake eliminates chain forks and block reorgs, guaranteeing payment finality upon confirmation.
2. **Native Fee Pooling**: One account can sponsor transaction fees for all transactions in an atomic group, allowing AI worker agents to execute with **zero native ALGO balance**.
3. **1KB Transaction Note Field**: Cryptographic execution evidence roots, TEE attestation digests, and payment receipts can be committed directly into Algorand's 1,024-byte transaction note without smart contract storage costs or state bloat.
4. **16-Transaction Atomic Groups**: Native atomic Delivery-vs-Payment (DvP) swaps payment against credential/resource delivery in a single round without intermediary escrows.

Currently, the Algorand ecosystem lacks a unified standard for HTTP 402 machine payments and note-field evidence anchoring. Developers resort to incompatible, proprietary implementations. ARC-0402 unifies these mechanisms into an interoperable standard for AI agents, servers, and payment facilitators.

### HTTP 402 Server Challenge

When an autonomous client requests a protected resource without valid payment, the server MUST respond with `HTTP 402 Payment Required`.

The response MUST include:
1. `Content-Type: application/json`
2. `PAYMENT-REQUIRED: algorand`
3. A JSON payload with the following schema:

```json
{
  "protocol": "x402.algorand/v0",
  "challengeId": "ch_7a8b9c0d1e2f3a4b",
  "network": "algorand-mainnet",
  "caip2": "algorand:wGHE2Pwdvd7S12BL5FaOP20EGYesN73ktiC1qzkkit8=",
  "recipientAddress": "AEAQCAIBAEAQCAIBAEAQCAIBAEAQCAIBAEAQCAIBAEAQCAIBAEA5RCDXMI",
  "requiredAsset": "USDCa",
  "assetId": 31566704,
  "amountMicroUnits": "10000",
  "receiptAnchorDigest": "c3ab8ff13720e8ad9047dd39466b3c8974e592c2fa383d4a3960714caef0c4f2",
  "notePrefix": "x402:receipt:v1:",
  "expiresAtRound": 65180000,
  "challengeDigest": "fa45b23d9c12e8736a54ef12bc0987456721de09bc87123456789abcdef01234"
}
```

#### Fields Definition:
- `protocol` (string, REQUIRED): MUST be `"x402.algorand/v0"`.
- `challengeId` (string, REQUIRED): Unique session or request identifier.
- `network` (string, REQUIRED): Algorand network name.
- `caip2` (string, REQUIRED): CAIP-2 chain identifier.
- `recipientAddress` (string, REQUIRED): Standard 58-character Algorand recipient address.
- `requiredAsset` (string, REQUIRED): `"ALGO"` or `"USDCa"` (or custom ASA symbol).
- `assetId` (integer, OPTIONAL): Algorand Standard Asset ID (omitted or 0 for native ALGO).
- `amountMicroUnits` (string, REQUIRED): Required amount in base micro-units (integer encoded as string to prevent 64-bit float precision loss).
- `receiptAnchorDigest` (string, REQUIRED): 32-byte hex-encoded SHA-256 digest of the request/resource execution evidence.
- `notePrefix` (string, REQUIRED): MUST be `"x402:receipt:v1:"`.
- `expiresAtRound` (integer, REQUIRED): Algorand round height after which the payment transaction MUST NOT be accepted.
- `challengeDigest` (string, REQUIRED): Cryptographic commitment over challenge parameters.

### Client Settlement Transaction

The client satisfies the challenge by constructing and submitting an Algorand transaction (or atomic group):

1. **Transaction Type**:
   - `Payment` (pay) for native ALGO.
   - `AssetTransfer` (axfer) for `USDCa` or other ASAs.
2. **Receiver**: MUST match `recipientAddress`.
3. **Amount**: MUST be greater than or equal to `amountMicroUnits`.
4. **Note Field Anchoring**:
   The `note` field of the transaction MUST begin with the UTF-8 bytes of `notePrefix` concatenated with the hex-encoded `receiptAnchorDigest`:
   ```
   Note = "x402:receipt:v1:" || <64-char hex SHA-256 digest>
   ```
   Total note length: $16 + 64 = 80\text{ bytes} \le 1024\text{ bytes}$.
5. **Round Validity Bounds**:
   - `FirstValid`: Current round on submission.
   - `LastValid`: $\le \text{expiresAtRound}$.

### Gasless AI Agent Execution (Native Fee Pooling)

Algorand natively allows fee sponsorship within an atomic transaction group without smart contracts.

To execute a gasless transaction for an autonomous worker agent:
1. **Transaction 0 (Fee Sponsor)**:
   - Sender: Sponsor / Facilitator account.
   - Receiver: Sponsor account (or payment receiver).
   - Fee: $2 \times \text{min\_fee}$ (2,000 microAlgos).
2. **Transaction 1 (Worker Agent)**:
   - Sender: Worker Agent account (holding ASA balance, zero native ALGO balance).
   - Receiver: Resource provider.
   - Fee: `0 microAlgos`.
3. **Atomic Grouping**:
   Both transactions are bundled into an atomic transaction group with a combined fee meeting the network requirement ($2,000 \ge 1,000 + 1,000$). The worker agent's transaction executes with zero native ALGO spent.

### 16-Transaction Atomic DvP (Delivery vs Payment)

For complex multi-party settlement (e.g. LLM inference compute verification, multi-agent escrow release, and payment clearing), clients and servers MAY compose up to 16 transactions in an atomic group:
- `Tx 0`: Resource / Compute attestation issuance (note anchoring).
- `Tx 1`: Client payment to Primary Provider.
- `Tx 2`: Facilitator fee micro-split.
- `Tx 3..N`: Sub-agent revenue distribution.

If any transaction in the group fails, the entire settlement reverts with zero state mutation.

### Verification Algorithm

Upon receiving the payment transaction ID or signed atomic group, the server MUST verify:

1. **Transaction Confirmation**: Retrieve transaction details from an Algorand node or indexer. Confirm `confirmed-round > 0`.
2. **Network Match**: Validate `genesis-hash` matches expected network.
3. **Recipient Match**: Validate `receiver` matches `recipientAddress`.
4. **Asset Match**: Validate `asset-id` matches `assetId` (or native ALGO transfer).
5. **Amount Sufficiency**: Validate `amount >= amountMicroUnits`.
6. **Round Freshness**: Validate `confirmed-round <= expiresAtRound`.
7. **Note Field Integrity**: Decode `note` field and assert:
   ```
   note.startsWith("x402:receipt:v1:") &&
   note.slice(16) === receiptAnchorDigest
   ```

If all assertions hold, the server MUST immediately release the protected resource and return `HTTP 200 OK`.

## Rationale

- **Why Transaction Note over Application State?**  
  Storing payment state in Algorand smart contracts requires state schema allocations, minimum balance requirements (MBR), and TEAL opcode overhead. Algorand's 1KB note field provides an immutable, consensus-verified data carrier at the baseline transaction fee (0.001 ALGO / ~$0.0002), eliminating smart contract state bloat.

- **Why Atomic Groups over Off-Chain Escrow?**  
  Algorand's native 16-transaction atomic groups guarantee atomic execution at the consensus level. Payment and receipt release are cryptographically bound without counterparty custody risk.

- **Why 6-Decimal Fixed Precision?**  
  Both ALGO (microAlgos) and native Circle USDC (`USDCa`) use 6 decimal places ($10^{-6}$), allowing unified integer arithmetic without floating-point precision loss.

## Backwards Compatibility

ARC-0402 is fully backwards-compatible with standard Algorand Consensus V2, AVM 10+, and standard algod nodes. It introduces no protocol-level consensus changes and works across existing wallets and indexers.

## Security Considerations

1. **Replay Protection via Round Expiry**: Servers MUST enforce `expiresAtRound` to prevent delayed transaction replay attacks.
2. **Digest Binding**: The `receiptAnchorDigest` MUST uniquely bind the specific resource, client session, and execution payload. A transaction with a mismatched digest MUST be rejected even if the payment amount is sufficient.
3. **Opt-In Requirements for ASAs**: Clients paying in ASAs (such as `USDCa`) MUST ensure the recipient account has opted into the asset ID before submitting payments. Servers MUST specify an address already opted into the designated asset.
4. **Genesis Hash Verification**: Implementations MUST strictly verify the network genesis hash to prevent cross-chain replay of transactions between MainNet and TestNet.
